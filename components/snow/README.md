# snow

snow-mock — the lightweight ServiceNow ITSM simulator the
[lightwell-workshop](https://github.com/rhpds/lightwell-workshop) uses
(upstream: [redhat-ads-tech/snow-mock](https://github.com/redhat-ads-tech/snow-mock)),
vendored under `files/snow-mock/` so this repo deploys comment-capable builds
without an image publish. The demo gets a ServiceNow-looking incident board
with zero ServiceNow.

## What this chart deploys

| Resource | Notes |
|---|---|
| Namespace `snow` | wave -2 |
| `snow-mock-code` / `snow-mock-static` ConfigMaps | the vendored app + SPA (code rolls the Deployment via checksum annotations) |
| `snow-mock` Deployment | UBI9 python-311; `pip install` into an emptyDir at first start (~20 s before readiness), gunicorn on 8080 |
| `snow-mock-state` PVC | incidents survive pod restarts (the workshop learned that lesson; see their PVC comment) |
| `snow-mock` Service + Route | `https://snow.<cluster subdomain>` |
| `snow-ui` ExternalSecret | the UI Basic-auth password from Vault (entry `snow-ui-password`, generated by vault-secrets) |
| `snow-register-apps` Job | registers the example applications on the board, idempotently |

## UI access

`https://snow.<cluster subdomain>` — HTTP Basic auth, username **demo**:

```sh
oc get secret tssc-snow-ui-password -n snow -o jsonpath='{.data.password}' | base64 -d; echo
```

The password is generated into Vault at install (nothing is a Helm value) and
materialized by ESO. `/api/v1/health` stays unauthenticated for kubelet
probes. Set `snow.auth.username: ""` to disable auth entirely (upstream
behavior — not recommended on a shared cluster). Keycloak fronting was
considered and deliberately not added: Basic auth keeps the component
self-contained; swap in an oauth-proxy if the demo outgrows it.

## Application registration

snow-mock has no CMDB API — an application "exists" as incidents whose
`cmdb_ci` names it. The registration Job creates one incident per
application in `values.yaml` (`applications`), with:

- `cmdb_ci` = `<gitGroup>/<application>` — the GitLab path, **the same
  convention the Automation Orchestrator integration stamps**, so a future
  AO ticket wiring finds these records without migration
- `guid` = `tssc-app-registration` — the idempotency marker (the Job skips
  apps whose registration incident already exists)
- a Markdown description naming the application and its GitLab project

Re-running (delete the Job, re-sync) is safe: existing registrations are
skipped.

## Deliberately absent

No Automation Orchestrator / EDA / ticket-workflow integration. The board is
display + registration only; wiring it to the orchestrator's incident
lifecycle (parent/child incidents, remediation comments) is future work and
should follow the lightwell-workshop's `integration-configmap` pattern.

## Vendoring

`files/snow-mock/` is a copy of
`automation/gitops/bootstrap-tenant/files/snow-mock/` from
rhpds/lightwell-workshop, with ONE local patch: optional HTTP Basic auth
(`SNOW_AUTH_USER` / `SNOW_AUTH_PASSWORD` env; empty user = upstream
unauthenticated behavior; `/api/v1/health` exempt). When pulling a newer
upstream, re-apply that patch — it lives at the top of `app.py` under a
clearly marked comment block.

chart.js is NOT vendored: at ~207KB it pushes the static ConfigMap past
the 256KB `metadata.annotations` limit (Argo's client-side apply stores
the whole manifest as `last-applied-configuration`; observed failing on
cluster-6vf9b as "Too long: may not be more than 262144 bytes"). The SPA
loads it from jsDelivr pinned to an exact version with a Subresource
Integrity hash in `index.html`; the pod needs egress for its pip install
anyway. Bump the version by updating the `src`, `integrity` (sha384 of
the file, base64) and keeping `crossorigin="anonymous"`.
